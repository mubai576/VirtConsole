# V3.0 重构方案：miuix 设计语言移植 + Vite/React 前端 + Rust 侧整理

- 目标：前端换用 miuix（HyperOS 风格）视觉语言，重建为 Vite + React；整理前端架构与 Rust 侧输入链路
- 范围：`ui/frontend` 全量重写；`ui/src` 输入链路与模块边界整理。采集/PVE/终端后端能力保持
- 约束：真机 PVE 无桌面环境，kiosk 全屏；**设计基准 2K，一等目标 2K/4K**，方向键为主输入
- 前提：miuix 是 Compose Multiplatform 的 Kotlin 库，**无 Web 实现**，故手写移植其设计语言
  （token 取自 miuix 源码 `miuix-ui/.../theme/Colors.kt`、`TextStyles.kt`、各 `*Defaults`）

## 二、分辨率策略（2K 基准 + 视口比例缩放）

### 2.1 先修一个现有缺陷

[shared.js:61](../ui/frontend/shared.js#L61) 的 `SCALE_ZOOM` 把 4K 定为 `1.35`、
2K 定为 `1.15`。但 4K(3840) 相对 1080p(1920) 线性是 **2.0×**、2K(2560) 是 **1.33×**。
按现表，4K 屏上 UI 只有应有物理尺寸的 67%（1.35/2.0），字和行都偏小 —— 这正是
"UI 效果不满意"的一部分成因。固定 zoom 表要换掉。

### 2.2 正确模型

十英尺场景下观看距离不变，同尺寸面板无论 1080p/2K/4K，元素都应占据**相同屏幕比例**，
即 px 需与视口宽度成正比。故：

```css
:root { font-size: calc(0.625vw * var(--vc-user-scale, 1)); }  /* 2560 → 16px */
```

全部 token 用 `rem`。得到的实际根字号：1080p → 12px、2K → 16px、4K → 24px，
三者物理尺寸一致。`--vc-user-scale` 供设置页做用户偏好（大字/紧凑），
`ui_scale` 配置项语义由"分辨率基准"改为"缩放倍率"（`auto/0.9/1.0/1.1/1.25`），
旧值 `720p/1080p/2k/4k` 迁移时映射为 `auto`。

### 2.3 token 值（2K 基准，1rem = 16px @2K）

| 用途 | miuix 原生 | 2K 基准 | rem | 1080p / 4K 实际 |
|---|---|---|---|---|
| 正文 Main | 17sp | 32px | 2 | 24 / 48 |
| 摘要 Body2 | 14sp | 26px | 1.625 | 19.5 / 39 |
| 页标题 Title2 | 24sp | 44px | 2.75 | 33 / 66 |
| 分组标题 SmallTitle | 13sp | 26px | 1.625 | 19.5 / 39 |
| 列表行高 | 56dp | 112px | 7 | 84 / 168 |
| 卡片圆角 | 16dp | 28px | 1.75 | 21 / 42 |
| 页面边距 | 16dp | 64px | 4 | 48 / 96 |
| 卡片间距 | 12dp | 32px | 2 | 24 / 64 |

相对 miuix 手机尺度约 1.9×（32/17），因方向键 + 远距离观看需要。

### 2.4 焦点态（miuix 没有，需自建）

miuix 为触摸/鼠标设计，无键盘焦点模型。定义：焦点 = `0.1875rem`(3px@2K)
`primary` 描边 + 背景提亮至 `surfaceContainerHighest` + `scale(1.015)`；
按下态沿用 miuix 的背景加深，两者视觉可区分。
miuix 动效是弹簧物理参数（`response`/`damping`，非贝塞尔），
CSS 用 `cubic-bezier(.32,.94,.6,1)` 250ms 近似。

## 三、技术决策

### 6.2 P1 落地记录（2026-08-16）

11 个组件落在 `ui/web/src/ui/`（方案 §4 的 `src/ui/`），样式统一在 `ui.css`，
经 `index.js` 出口；视图只 import 组件，不碰样式文件。

约定三条：

1. **焦点不用 `:focus`**。组件收 `focused` 布尔属性，渲染 `.vc-focused`。
   DOM 焦点由 P2 的 FocusProvider 托管，这样一个视图内的高亮是纯派生状态，
   "单高亮不变量"断言仍然成立。唯一例外是 `TextField` —— 输入框必须拿真实 DOM 焦点，
   否则按键进不去，故它在 `focused` 变化时自己 focus/blur，调用方需同期挂起方向键导航。
2. **Slider 不自己吃按键**，只导出 `nudge(value, dir, opts)`。组件内再抢一层
   `keydown` 会和 FocusProvider 打架。
3. **NavigationBar 同时输出新旧类名**：`mx-navitem` + `tab` / `focus` / `active`，
   容器 `id="tabbar"`，保住 `helpers.js` 的 `#tabbar .tab.focus`。改这些类名必须同步测试。

`Dialog` 用 capture 阶段监听并 `stopPropagation`，打开期间按键不漏到底层视图，
一次替掉旧 `shared.js` 里 6 种模态。

**缩放模型已量化验证**（`0.625vw`，行高 `7rem`）：

| 分辨率 | 1rem | 行高 | 正文 | 行高/视口宽 |
|---|---|---|---|---|
| 1080p | 12px | 84px | 24px | 4.375% |
| 2K | 16px | 112px | 32px | 4.375% |
| 4K | 24px | 168px | 48px | 4.375% |

三档占屏比例一致，即 §2.2 要的效果。对比旧 `SCALE_ZOOM`：4K 下行高
`56 × 1.35 = 75.6px`，仅占 1.969% 视口宽 —— 比应有尺寸小 2.2 倍。
这是"UI 效果不满意"可量化的主因。

**已验证**：`npm run build` 通过（45 模块，CSS 10.8KB / JS 203KB）；67 个 token
在压缩产物中完整；`cargo build -p vc-ui` 通过；Windows 下预览页渲染正常。
**未验证**：2K/4K 真机目视 —— 本机开发窗口 1280×720 会落到 `max-width: 1280px`
兜底档（1rem = 8px），只能验证结构不能验证观感，留到 P5 上 HDMI 确认。

### 6.3 P2 落地记录（2026-08-16）

**验收达成**：`VIRTCONSOLE_TEST=1 cargo run -p vc-ui` → `75/75 通过`
（74 场景 + `driver_started`），连续三次运行结果一致。§6.1 关掉的测试灯已重新点亮。

**两处偏离方案**（均已在代码注释中写明原因）：

1. **模态保持命令式**（偏离 §4 的 `Dialog.jsx`）。调用点全是 `if (!await
   showConfirm(...)) return;` 这类线性 async 流；套件 G/H 有 20+ 场景断言
   `.modal` / `.form-row` 的 DOM 结构与 inline `display` 显隐。改 React 要给
   每个视图加状态机，且这些断言得重写。`ui/web/src/lib/modal.js` 承接旧
   `shared.js` 的实现，`Dialog.jsx` 暂未使用。
   React 下"抹掉底层 `.focused`"失效（下次渲染会加回来），故新增
   `lib/modalState.js` 深度计数，由 `useFocusable` 读它让视图自行不渲染高亮
   —— 这是套件 H6「模态内单高亮」的实现方式。
2. **console 层从 P3 提前**（仅搬结构，不含 §5.1 输入修复）。套件 I、G5、L
   需要 `#console-layer` 与 `#vm-canvas` 存在，否则这三组无法运行。§5.1 仍留 P3。

**三处测试改动**（§7 要求同步记录，不得静默）：

| 文件 | 改动 | 原因 |
|---|---|---|
| `suites/g-settings.js` | `G4_resolution_apply_zoom` → `G4_scale_apply_user_scale` | §2.2 删掉了 `documentElement.style.zoom`，改断言 `--vc-user-scale` 与根字号区间 |
| `framework.js` `hover()` | 追加派发冒泡的 `mouseover` | React 的 `onMouseEnter` 由根节点 `mouseout`/`mouseover` 委托合成，只发不冒泡的 `mouseenter` 触发不到（旧实现是元素上的原生监听） |
| — | 其余 11 套件与 `framework.js` 其他部分未改 | 回归网保持原样 |

**三个非确定性根因**（曾在 48/75–73/75 间随机浮动，均已修）：

1. **Tab 栏光标与已激活视图曾是同一状态**。`.tab-view.active` 从 `current` 派生，
   于是 Tab 栏 ←→ 会挪动 `.active`；而 `helpers.gotoTab` 用 `activeTabId()`
   推算要按几次 → ，按键次数全错（F/G/H 连锁失败）。改为 `current`（光标）与
   `activeId`（已激活）两个 state。
2. **用 `rAF` 派发 `onFocus`**。窗口未合成时 `rAF` 被节流甚至暂停，`onFocus`
   迟到会让"切 Tab 后立刻按键"落在旧状态上。改为同步派发（四视图常驻挂载 +
   `useLayoutEffect` 注册，此刻注册表必然就绪）。
3. **套件 E 污染其后所有套件**。终端退出钩子只在挂载 effect 里注册一次，
   首次 Ctrl+Alt+Q 用掉后重进不再注册，第二次 Ctrl+Alt+Q 找不到钩子，
   xterm 保住 DOM 焦点并吞掉后续全部按键。改为由 `termActive` 单一 effect
   同时派生终端焦点与退出钩子。

**已验证**：`npm run build` 通过（83 模块，CSS 25.2KB / JS 243.8KB + driver 25.9KB）；
`cargo build -p vc-ui` 通过；全套件三次 75/75。
**未验证**：真机 Win10 键鼠仍是 5ad9fe9 的待办，属 §5.1 / P3 范围。

## 七、风险

- **4K 采集带宽**：4K 全帧 3840×2160×4 = 33MB，base64 后约 44MB/帧过 IPC，
  1080p 现为 8.3MB。差分推送（commit 35f597b）在 4K 下是必需项而非优化项；
  若首帧或大面积更新卡顿，需评估二进制通道（Tauri IPC raw / 共享内存）替代 base64。
- **WebKitGTK 兼容**：真机 WebKitGTK 对 React 19 的 ES 目标支持待确认，
  `vite build --target` 可能需降至 es2020。
- **canvas 帧路径**：React 化后须确认没引入额外重绘，
  现有 ImageData 缓存优化（commit 02dc5f7）必须保留。
- **zoom → rem 迁移**：`zoom` 影响 canvas 与 xterm 的坐标换算；
  改 rem 后鼠标绝对坐标映射（`capture_mouse_move`）与终端尺寸需重新校验。
- **测试选择器**：迁移中若某选择器无法保留，需同步改套件并记录，不可静默改。
