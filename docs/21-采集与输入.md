# 采集与输入

> - 类型：规范（长期有效）
> - 权威范围：本文是**三模采集技术链路、QMP 与 D-Bus 协议细节、keycode 约定**的唯一来源。
>   产品层定义见 [10-产品需求PRD.md](10-产品需求PRD.md) §3.4；模块边界见 [20-架构总览.md](20-架构总览.md)
> - 最后核实：2026-08-16（对照 commit 080c50c）
> - 验证记录：[90-历史记录.md](90-历史记录.md)

## 一、三模对照

| | 模式 1 | 模式 2 | 模式 3 |
|---|---|---|---|
| 名称 | QMP screendump | dbus-display 像素事件 | IVSHMEM 共享内存 |
| 适用 | 办公 / 低负载 | 无直通 / 需流畅画面 | VFIO / SR-IOV 直通 |
| 机制 | 轮询 `screendump` 取 PPM | QEMU 经 D-Bus 推 `Scanout`/`Update` | VM 内 Agent 抓帧写共享内存 |
| VM 内需装东西 | 否 | 否 | **是**（DXGI Agent） |
| 实测帧率 | ~1.5ms/帧 @720×400 | **85fps** @720×400 | 原生 60fps（未实现） |
| 状态 | ✅ 已接入 | ✅ 链路已通 | ⬜ 未开始（缺硬件） |

模式由 VM 显卡配置决定：普通 VGA → 模式 1；Virtio-GPU → 模式 2；SR-IOV/VFIO 直通 → 模式 3。
**不可运行时热切换**，改模式需改 VM 配置并重启 VM。

## 二、模式 1：QMP screendump

- QEMU 的 `screendump` 走 QMP，输出到文件后由 Rust 读回
- **PVE 的 QEMU 未编译 libpng**，PNG 格式不可用，只支持 PPM（原始 RGB）。
  这反而是简化：免 PNG 编解码，可直接喂 Canvas
- 帧率标定：720×400 文本模式 10 帧共 15ms（~1.5ms/帧）；1080p 按像素等比估算 ~10ms/帧
- 轮询间隔由 `capture_fps`（5/10/15）控制

## 三、模式 2：dbus-display

### 3.1 QEMU 启动参数

```text
-display dbus[,addr=<dbusaddr>|p2p=yes][,gl=on|off|core|es]
```

- `addr=`：连接已有 D-Bus 总线，QEMU 以 `org.qemu` 名注册
- `p2p=yes`：QEMU 等客户端，经 QMP `add_client` 传入 Unix socket FD 建 peer-to-peer
- `gl=on`：帧以 DMABUF FD 共享；`gl=off`：退回原始像素 `Scanout`

**本项目用 `gl=off`**，原因见 §3.5。

### 3.2 D-Bus 对象树

根 `/org/qemu/Display1`：

| 对象 | 内容 |
|---|---|
| `/VM` | 属性 `Name` `UUID` `ConsoleIDs:au` `Interfaces:as` |
| `/Console_$id` | 属性 `Label` `Head` `Type` `Width` `Height` `DeviceAddress` `Interfaces`；方法 `RegisterListener` `SetUIInfo`；可选 Keyboard / Mouse / MultiTouch 接口 |

### 3.3 Listener 注册（Unix 实际签名）

1. 客户端 `socketpair(AF_UNIX, SOCK_STREAM)` 取两端 fd
2. 一端交给 QEMU（bus 模式经 `RegisterListener(h)` 传 FD；p2p 模式经 QMP `add_client`）
3. QEMU 在 fd 上以 **AUTHENTICATION_SERVER** 建连接，客户端在另一端实现
   `org.qemu.Display1.Listener`（对象路径 `/org/qemu/Display1/Listener`）
4. 通过 Listener 的 `Interfaces` 属性声明支持哪些能力

> 文档里的 `(ay listener, h listener)` 是 **Win32 变体**；Unix 只传 `h`。

### 3.4 Listener 事件

| 事件 | 载荷 | 用途 |
|---|---|---|
| `Scanout(w,h,stride,pixman_format,data:ay)` | 全帧原始像素 | gl=off 主路径 |
| `Update(x,y,w,h,stride,pixman_format,data)` | 局部更新 | 脏区域差分 |
| `ScanoutMap(handle:h,offset,w,h,stride,format)` | 共享内存 map | Unix 可选接口 |
| `ScanoutDMABUF(dmabuf:h,w,h,stride,fourcc,modifier:t,y0_top:b)` | DMABUF FD | gl=on 主路径（本项目不用） |
| `ScanoutDMABUF2(planes…)` | 多平面变体 | — |
| `Disable()` / `MouseSet()` / `CursorDefine()` | — | 状态与光标 |

### 3.5 为什么不用 gl=on 零拷贝（重要）

真机实测（RTX 5070 Ti + nvidia-open）：

- `eglCreateImageKHR`（`EGL_LINUX_DMA_BUF_EXT`）对 QEMU virgl 产出的
  `modifier=0x0300000000E08014`（XB24）返回 **`EGL_BAD_MATCH (0x300c)`**
- `eglQueryDmaBufModifiersEXT` 显示该 modifier 在驱动支持列表内，
  但**所有 NVIDIA 私有 modifier（`0x0300000000xxxxxx` 系列）`external_ok=no`**
  —— 只有 linear（modifier=0）可外部导入
- 结论：**NVIDIA 私有 tiled 格式只允许驱动内部使用**，
  外部进程（我们的 Rust 应用）无法 EGL 导入

三条对策：

| 方案 | 状态 | 说明 |
|---|---|---|
| **A：`gl=off` + Scanout/Update 像素事件** | ✅ **在用** | 实测 85fps；数据形态与模式 1 一致，前端零改动；无 GPU 私有格式依赖，三家通用 |
| B：让 virgl 输出 linear dmabuf 再 EGL 导入 | ⚠️ 待评估 | 作为性能增强。`GBM_ALWAYS_SOFTWARE=1` 实测未改变输出，需更深入 virgl 配置 |
| C：IVSHMEM（模式 3） | 远期 | 走共享内存，不受此限制 |

### 3.6 PVE VM 接入

VM 需在启动参数注入 `-display dbus`。实测 **与默认 vnc 共存无冲突**（`qm showcmd` 验证）。

- 手动：VM config 加 `args: -display dbus`
- 应用内：操作页「启用/禁用 dbus 采集」按钮，调 `pve_vm_enable_dbus` / `pve_vm_disable_dbus`
  写/删 args。**需停机重启 VM 生效**

用户操作路径：启用 dbus 采集 → 重启 VM → 进入采集。

### 3.7 会话生命周期

```text
ConsoleLayer.enter(vmid, { capture })
  └─ 先 capture_start ──→ 再显示画面 ──→ 再 vm_connect
```

**顺序不可颠倒**：`input_bus` 只在 `capture_start` 成功时写入，
先进层再采集会让中间的按键被判「未连接 VM」丢掉。

**采集失败不阻断进层**：键盘走 QMP 回退，只是没有像素流，并 toast 说明。

VM 停机 → D-Bus 对象消失 → 采集自动停止并提示。

## 四、输入

### 4.1 路由

```text
前端 KeyboardEvent.code ──IPC──→ input.rs
                                  ├── input_bus + console_path 都在 → D-Bus
                                  └── 否则 → QMP
```

前端只发 `code`，**不做分支判断**。历史上前端写过 `if (e.code) dbusKey() else qmpKey()`，
但 WebKitGTK 下 `e.code` 恒真，else 分支从来没执行过 —— 回退逻辑必须在 Rust 侧。

### 4.2 QMP `input-send-event` 真实格式

经真机 + `query-qmp-schema` 确认：

- 参数是 `events` **数组**（可批量）
- 键值是 QAPI alternate：`{"type":"qcode","data":"a"}`（或 number）
- 事件判别值：`key` / `abs` / `rel` / **`btn`**（按钮不是 `"button"`）

### 4.3 D-Bus 键盘的 keycode 是 XT set1 scancode（易错点）

`org.qemu.Display1.Keyboard.Press/Release` 收的**不是 Linux evdev keycode，
而是 XT set1 scancode**。按 evdev 填会让方向键 / 功能键 / 编辑键全错。

已钉住的具体值（单测 `xt_set1_not_evdev_for_arrows_and_edit_keys`）：

| 键 | XT set1 |
|---|---|
| ArrowUp | 72 |
| Home | 0x47 |
| F11 | 87 |

映射表在 `capture/keymap.rs`，**不挂 `cfg(unix)`** —— 挂上就等于在开发机永远测不到，
提交 `f173f50` 的方向键 bug 正是这么漏到真机的。理由见 [20](20-架构总览.md) §二。

### 4.4 鼠标

- 移动：`SetAbsPosition` 绝对坐标（canvas `mousemove` → 换算）
- 按键：`mousedown`/`mouseup` → 按钮事件
- 指针移动是高频事件，不进日志环，但与按键共用「首次失败可见」闸门
  —— 指针不动必须能被用户看到

### 4.5 可打印字符走文本通道

可打印字符走 `capture_input_text`，**不重复走按键通道**。
`text_to_key_events` 已覆盖完整美式键盘可见 ASCII（含全部标点与 shift 组合），非 ASCII 跳过。

### 4.6 退出沉浸层补发抬起

只按下没抬起就 `Ctrl+Alt+Q`，guest 侧修饰键会一直按住。
退出时补发卡住按键的抬起事件，失败留日志痕迹。

`Ctrl+Alt+Q` 本身不转发给 VM。

### 4.7 错误可见性

首次输入失败经 toast 上报（只报一次，避免连击刷屏），每次进沉浸层重置闸门。
kiosk 无 devtools，`console.error` 等于错误不存在 —— 用户只会看到「按键没反应」。

## 五、风险

| 风险 | 说明 | 对策 |
|---|---|---|
| **4K 采集带宽** | 4K 全帧 3840×2160×4 = 33MB，base64 后 ~44MB/帧过 IPC（1080p 现为 8.3MB） | 差分推送是**必需项**而非优化；若首帧或大面积更新卡顿，评估二进制通道（Tauri IPC raw / 共享内存）替代 base64 |
| 坐标换算 | `zoom` → `rem` 迁移影响 canvas 与 xterm 坐标 | ✅ canvas 已修（2026-08-17）。**2026-08-16 曾误划为「已排除」**：当时只复核了对 `zoom`/`rem` 免疫，漏了 `object-fit`——canvas 是替换元素，`contain`（默认缩放档 `fit`）会等比缩放并居中留黑边，元素框 ≠ 画面，真机上表现为指针偏移 + 移动幅度被压缩。现由 [`mapToGuest()`](../ui/web/src/console/useInputForward.js) 按真实画面矩形换算并夹取到 `[0, w-1]`，覆盖 `contain`/`fill`/`none`/`cover`；守卫见套件 `I2b_pointer_maps_to_guest_pixels`。xterm 尺寸仍需 P5 目视 |
| canvas 重绘 | React 化后须确认没引入额外重绘 | 保留既有 ImageData 缓存优化（commit `02dc5f7`） |
| `org.qemu` 名冲突 | 多 VM 连同一 dbus bus 会撞名 | 单 VM 采集，或用 p2p / 自定义总线地址 |
