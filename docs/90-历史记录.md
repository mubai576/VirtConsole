### 2026-08-17 — 「前端键鼠无效」的真因：共享总线活在 vc-ui 的 cgroup 里

**推翻 5ad9fe9 的结论。**那条记的「spike 直连有效 vs 前端无效」不是前端问题，
前端链路一直是好的。真因在部署：

`dbus-daemon` 由 `virtconsole.service` 的 `ExecStartPre` fork，落进该服务的 cgroup。
`systemctl stop virtconsole` 杀 cgroup 时总线一起死、socket 被删；下次启动又在
同一路径起一个**新**总线，而此前已挂上来的 QEMU 仍连在那个**死**总线上。
新总线上再也看不到 `org.qemu`，`capture_start` 必然失败。
spike 跑在原总线还活着的时候；等测前端时已重启过服务，QEMU 早被孤立。

修法（f969574 / 44d79c6）：总线独立成 `virtconsole-dbus.service`，生命周期比 vc-ui 长；
`install.sh` 的 install/remove 带上它，`check` 新增一条查总线持有者 cgroup，拦住回归。

**真机证据**（VM 9000 新起、附到活总线）：`capture_start` 走完
`已连接 D-Bus → VM 代理 → ConsoleIDs=[0] → RegisterListener OK → p2p OK`，
`Scanout 720x400` 有真实帧；输入 `started=true status=true ready=true`，
按键全部 `ok===true`；全量 **86/86**；停 vc-ui 后总线存活。

**同时查出三处「假绿」与陈旧部署**：

- `/usr/local/bin/vc-ui` 停留在 08-09 18:59，而 keycode 修复 f173f50 是 19:13 提交的
  —— 服务跑的二进制**早于**修复 14 分钟。`install.sh:85` 的安装步骤在修复后从未执行。
  此前一切「经服务验证」的结论都建立在这个旧二进制上。
- 单元里写死 `VIRTCONSOLE_AUTOCONNECT_VMID=9000`，而配置里是 9200。
  **不构成故障**：`commands/app.rs:20` 的优先级是 config 优先、环境变量兜底，
  所以实际自连的一直是配置里的 9200。查证过程中我曾误判成「环境变量盖掉配置、
  服务连的是停机的 9000」——方向是反的，记此以免后人照抄。
  该行已删（死设置容易被当成真相），自连目标交给 `config.json`。
- L7 曾 **6/6 全绿而 guest 一个键都没收到**：入口点 `Home.jsx:43` 进的是
  `enter(9000)` 且不带 `capture:true`，加上原断言只要求「ok 或留下 err」，
  后端报错也算通过。已收紧 + 新增强断言场景（见 [40-测试规范.md](40-测试规范.md)）。

**方法论教训（值得单独记）**：`screendump` 在 `vga: virtio` + `-display dbus` 下
返回的是 QEMU 最后一次已知的 scanout 表面；没有 D-Bus listener 挂着时它是**陈旧**的。
我据此得出的「画面零变化 → 前端没投递输入」不成立 —— 同一 md5 隔 21 分钟不变，
而 guest 明明在执行（6 秒 +20 CPU tick）。用 `sendkey` 做的对照也不算数：
差异 0.184% ≈ 1450 px ≈ 一个光标，动的是 QEMU 侧光标叠加层，不是 guest 重绘。
**结论：验证采集/输入链路不能用 `screendump` 当观测手段，要用 vc-ui 自己的 listener。**

### P4 — Rust 模块拆分｜单测 14 → 30

`capture.rs`(616 行) 与 `lib.rs`(659 → 141 行) 拆完，`cargo test --workspace` 30+7 通过，全套件 80/80。

**补记（2026-08-17）**：上面那句「拆完通过」只对 Windows 成立。真机一编就是
**22 个错误** —— `session.rs` 漏了 `use super::frame::{...}`，`CaptureState` 的
`input_bus`/`console_path` 在 `dbus_input` 变成兄弟模块后需要 `pub(super)`。
拆分当天把 unix 分支的编译状态写成已验证是错的（当时它确实编不过，见 b2f0153）。
教训：`cfg(unix)` 分支的「通过」只能由真机 `cargo build` 背书，开发机零警告说明不了它。

三处偏离原方案，都是为了**让纯计算代码在 Windows 开发机上也能编译测试**：

- capture 拆**五**个文件而非四个，多出 `session.rs` 承载 socketpair/Listener/start/stop。
  四文件方案要求 `mod.rs` 自己带 session 逻辑，那部分必须 `cfg(unix)`，于是整个
  `mod.rs` 被 gate 掉，`keymap`/`frame` 在 Windows 上进不了编译。
- `keymap`/`frame` **不挂 `cfg(unix)`**——纯查表与像素计算，挂了等于宣布永远测不到。
  f173f50 的「方向键全错」就是这么漏到真机的。Windows 上无消费者，
  用 `#![cfg_attr(not(unix), allow(dead_code))]` 消警告。
- `capture/input.rs` 改名 `dbus_input.rs`，避免与 P3 的 `ui/src/input.rs`（选 sink 层）撞名。

**拆分中查出真 bug**：`DirtyState::merge_rect` 包围盒算成 `rx.max(x+w)`，取的是旧矩形**左**边界。
新脏区落在左上方时右下边界被截 → 画面残留旧像素。改为 `(rx+rw).max(x+w)`。
原 616 行单文件里没有任何测试能碰到这段。

命令按 **State 依赖**分文件（非按数量均分）：`commands/{app,browser,vm,capture,config,pve,term}.rs`。

未验证：`session.rs`/`dbus_input.rs` 的 unix 分支本机无法编译（同 P3），留 P5。

### P3 — 输入链路修复｜80/80

[V2.0 §6.3 的「spike 直连有效、前端无效」悬案](#v20-dbus-display-采集2026-08-09) 三处根因逐条修掉：

1. **时序**：`ConsoleLayer.enter()` 内部先 `capture_start` 再显示画面再 `vm_connect`。
   旧路径中间的按键被判「未连接 VM」丢掉。采集失败**不阻断**进层（键盘走 QMP 回退 + toast）。
2. **回退失效**：前端 `if (e.code) ... else qmpKey(...)` 的 else 分支**从来没执行过**
   ——WebKitGTK 下 `e.code` 恒真。回退下沉到 Rust `ui/src/input.rs`：
   `input_bus` + `console_path` 都在则 D-Bus，否则 QMP。
   `capture_input_key/text/ready` 改为**两平台都注册**（此前 `cfg(unix)` 让非 unix
   拿到「命令不存在」而非输入层错误，正是第 3 条的来源）。
3. **错误不可见**：`useInputForward` 每次进层重置闸门，首个失败经 toast 上报（只报一次）。
   指针移动不进日志环但共用同一闸门——指针不动必须能被看到。

顺带修掉：退出沉浸层补发卡住按键的抬起；**监控高亮的轮询回灌**（离开 Tab 后 `row` 仍是
`"content"`，3s 内下一次轮询把 `.focused` 贴回监控卡 → 随机多高亮失败；改为完全派生自
`(hasFocus, row, cidx, sub)`）。

新增套件 L7「输入转发链路」5 场景，与 L1–L6 分开导出。框架改动一处：`keyup(k, opts)` 加 `opts`。

未验证：**真机 Win10 键鼠**。本机 Windows 恒走 QMP 分支；交叉编译 linux-gnu
受阻于 `libdbus-sys`/`ring` 缺 `x86_64-linux-gnu-gcc`。留 P5。

### P2 — FocusProvider + 4 视图迁移｜75/75

§6.1 关掉的测试灯重新点亮，连续三次一致。

两处偏离方案：

- **模态保持命令式**（`lib/modal.js`，`Dialog.jsx` 暂未使用）。调用点全是
  `if (!await showConfirm(...)) return;` 线性 async 流；套件 G/H 有 20+ 场景断言
  `.modal`/`.form-row` 的 DOM 与 inline `display`。React 下「抹掉底层 `.focused`」
  失效（下次渲染加回来），故加 `lib/modalState.js` 深度计数，由 `useFocusable` 读它。
- **console 层从 P3 提前**（仅搬结构，不含输入修复）——套件 I/G5/L 需要
  `#console-layer` 与 `#vm-canvas` 存在。

**三个非确定性根因**（曾在 48/75–73/75 随机浮动）：

1. Tab 栏光标与已激活视图曾是同一状态，Tab 栏 ←→ 会挪动 `.active`，
   `helpers.gotoTab` 推算的按键次数全错。改为 `current` / `activeId` 两个 state。
2. **用 `rAF` 派发 `onFocus`**：窗口未合成时 rAF 被节流甚至暂停，`onFocus` 迟到
   → 「切 Tab 后立刻按键」落在旧状态。改为同步派发。
3. **套件 E 污染其后所有套件**：终端退出钩子只在挂载 effect 注册一次，首次
   Ctrl+Alt+Q 用掉后重进不再注册，xterm 保住 DOM 焦点吞掉后续全部按键。
   改为由 `termActive` 单一 effect 同时派生终端焦点与退出钩子。

测试改动两处（不得静默）：`G4_resolution_apply_zoom` → `G4_scale_apply_user_scale`；
`hover()` 追加派发**冒泡的 `mouseover`**（React `onMouseEnter` 由根节点委托合成）。

## M2.5 前置技术验证（2026-08-09）

真机 192.168.0.20，PVE 9.x / QEMU 11.0.0-3。**C1–C5 全过，C6 部分通过。**

| 判据 | 结果 |
|---|---|
| C1 QEMU 支持 dbus-display + GL | ✅ PVE 自带 QEMU 11 的 `-display help` 含 `dbus`，GL 库齐备，**无需自编译 QEMU** |
| C2 D-Bus 对象树可见 | ✅ `VM.ConsoleIDs=[0]`，Console_0 `Type=Graphic`，接口 Keyboard/Mouse/MultiTouch |
| C3 注册 Listener 收事件 | ✅ 收到 `MouseSet`/`Scanout`/`ScanoutDMABUF` |
| C4 收到 ScanoutDMABUF | ✅ `gl=on` 下 20s 收 109 帧，fd 经 D-Bus 成功传给 Rust 探针 |
| C5 帧活性 | ✅ **远超目标**：`gl=off` 下 15s 收 425 帧（**~85fps**），分辨率随客户机模式实时切换 |
| C6 DMABUF 导入渲染 | ⚠️ 见下 |

**C6 关键发现——NVIDIA 私有 modifier 不可外部 EGL 导入**：
`eglCreateImageKHR` 对 virgl 产出的 `modifier=0x0300000000E08014` 返回 `EGL_BAD_MATCH (0x300c)`。
该 modifier 在驱动支持列表中，但所有 NVIDIA 私有 modifier（`0x0300000000xxxxxx`）
`external_ok=no`——**仅 linear（modifier=0）可外部导入**。
故 `gl=on` 零拷贝在**外部进程**不可行。对策与选项表见 [21-采集与输入.md](21-采集与输入.md) §3.5。

其他成果：D-Bus Keyboard `Press/Release` 调用成功客户机响应；
克隆 VM 9000→9100，`qm showcmd` + sed 换 `-vnc`→`-display dbus,gl=on` 手工启动成功
——证明 PVE VM 可通过自定义 args 接入。

探针迭代修掉 4 个坑：`ConsoleIDs` 需 zbus 显式 `name`（默认转 `ConsoleIds`）；
`ScanoutDMABUF`/`UpdateDMABUF` 同理（zbus PascalCase 会变 `ScanoutDmabuf`）；
socketpair fd 需 `O_NONBLOCK` 才能被 tokio 注册；**先 `RegisterListener` 再建 p2p 连接**
（否则 zbus `build()` 等对端应答挂起）。
