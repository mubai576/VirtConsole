# 部署与运维

> - 类型：规范（长期有效）
> - 权威范围：本文是**真机部署步骤、systemd 服务定义、构建链、故障排查**的唯一来源。
>   测试机地址与凭据见 [51-测试环境.md](51-测试环境.md)；架构与环境变量含义见 [20-架构总览.md](20-架构总览.md)
> - 最后核实：2026-08-16（对照 `scripts/install.sh`、`deploy/*.service`）

## 一、目标形态

单台 PVE 宿主机，开机后 HDMI 直接显示本应用全屏界面。**无桌面会话、无容器、无 X11**：
Weston 以 DRM 后端 + kiosk-shell 直接吃显示器，应用是它唯一的客户端。

三个 systemd 服务，均 `WantedBy=multi-user.target`：

| 服务 | 作用 | 用户 |
|---|---|---|
| `virtconsole-weston.service` | Weston 合成器（占 HDMI，`Conflicts=getty@tty1`） | `virtconsole`（补充组 video/render/input/tty） |
| `virtconsole-dbus.service` | 共享 session bus（QEMU dbus-display ↔ vc-ui 采集） | root |
| `virtconsole.service` | 应用本体，`Requires=`+`After=` Weston 与 dbus | **root**（见下） |

**应用暂以 root 运行**：QMP socket `/var/run/qemu-server/<vmid>.qmp` 只有 root 可读写。
待改为组授权（ACL）后可降权回 `virtconsole`。这是已知的权限债，不是设计意图。

`XDG_RUNTIME_DIR=/run/virtconsole`（由 `RuntimeDirectory=virtconsole`，模式 0700 创建）
——不要用 systemd 的 `%U` 展开，见 §六。

## 三、部署步骤

`scripts/install.sh` 是唯一入口，三个子命令：`install`（默认）/ `check` / `remove`。

```bash
sudo ./scripts/install.sh          # 装依赖 + 建用户 + 部署 systemd + 安装 vc-ui + 写默认 config
sudo ./scripts/install.sh check    # 环境自检（= scripts/check.sh）
sudo ./scripts/install.sh remove   # 停服务、删二进制与配置，保留系统包（无损）
```

### 3.1 依赖

```text
运行时：weston wayland-protocols mesa-utils pciutils seatd
构建：  build-essential pkg-config libgtk-3-dev libwebkit2gtk-4.1-dev \
        libayatana-appindicator3-dev librsvg2-dev
前端：  Node >= 20.19（Vite 7 要求；Debian 12 自带 18 过旧）
```

Node 不够新时脚本会提示装法：
`curl -fsSL https://deb.nodesource.com/setup_22.x | bash - && apt-get install -y nodejs`

构建依赖安装失败不中断（`|| true`），因为构建通常在另一台机器上做。

### 3.2 构建链（顺序不能反）

```bash
cd ui/web && npm ci && npm run build     # → ui/dist/
cargo build --release -p vc-ui           # Tauri 把 ui/dist 打进二进制
```

**`ui/dist/` 不提交仓库**，所以裸跑 `cargo build` 会因缺前端产物失败。
`install.sh` 的 `build_web()` 与「完整构建」路径封装了这个顺序，构建机上用它而不是裸 `cargo build`。
详情见 [31-前端架构.md](31-前端架构.md) §六。

### 3.3 NVIDIA 驱动（关键，容易踩）

1. 启用 Debian `non-free` 组件与 Proxmox `pve-no-subscription` 源
2. 添加 NVIDIA 官方 apt 源（CUDA repo，用 `debian12` 目录），安装 **`nvidia-open`**
3. `/etc/modprobe.d/virtconsole-nvidia.conf`：

   ```text
   blacklist nouveau
   options nvidia-drm modeset=1
   ```

4. `update-initramfs -u` 后重启

**三条硬结论**：

- **Blackwell（RTX 50 系）必须用 NVIDIA 开源内核模块**。闭源版直接拒载：
  `RmInitAdapter failed: requires use of the NVIDIA open kernel modules`
- 驱动 **550 无法编译到内核 7.0**（`VMA_LOCK_OFFSET` API 变更），610 可以
- 610 编译时可能撞 gcc-14 偶发内部错误（IRA pass 段错误），**重试 DKMS build 即过**

驱动就位的标志：`/dev/dri` 出现 `card1` + `renderD128`，`HDMI-A-1` 连接器 connected。

### 3.4 D-Bus 共享总线（模式 2 必需）

总线由**独立单元** `virtconsole-dbus.service` 持有：

```text
DBUS_SESSION_BUS_ADDRESS=unix:path=/run/virtconsole/dbus
ExecStart=/usr/bin/dbus-daemon --session --nofork --address=unix:path=/run/virtconsole/dbus
```

**总线必须比 vc-ui 活得久 —— 这是硬约束，别改回去。**
曾由 `virtconsole.service` 的 `ExecStartPre` fork，于是 daemon 落进该服务的 cgroup：
`systemctl stop virtconsole` 杀 cgroup 时总线一起死、socket 被删；下次启动在同一
路径起一个**新**总线，而此前已挂上来的 QEMU 仍连在那个**死**总线上 ——
新总线上再也看不到 `org.qemu`，`capture_start` 必然失败，且症状看起来像
「前端输入无效」。排查这条弯路的完整记录见 [90-历史记录.md](90-历史记录.md)。

`install.sh check` 会验证总线持有者的 cgroup 是否为 `virtconsole-dbus`，拦住回归。

**已挂上来的 QEMU 无法迁到新总线**：`-display dbus` 在 VM 启动时定型，
总线换了就得重启该 VM（`qm stop` + `qm start`）才能重新注册 `org.qemu`。

不声明 `RuntimeDirectory=virtconsole`：那会让 systemd 在单元停止时删掉整个
`/run/virtconsole`，而 Weston 的 `wayland-0` 也在那里。

QEMU 的 `-display dbus` 与应用必须挂**同一条总线**，否则 `dbus-display` 采集连不上。
QEMU 侧参数见 [21-采集与输入.md](21-采集与输入.md) §三。

#### 一条总线只能有一台 dbus-display VM

`org.qemu` 是 D-Bus **well-known name**，同一条总线上只有一个持有者。多台 VM
都用 `addr=unix:path=/run/virtconsole/dbus` 启动时，**先启动的那台抢到名字**，
后启动的只能排队（`ListQueuedOwners` 里看得到），永不生效。

而 `capture::session::start()` 只接受 `bus_addr`，**不接受 vmid**；
`session.rs` / `dbus_input.rs` 里所有代理都写死 `default_service = "org.qemu"`。
于是采集连的是「抢到名字的那台」，跟界面上进的是哪台无关。

后果，按严重度排：

1. **多台 VM 同挂一条总线时，键鼠会打到错的 VM 上。** 界面显示 A、输入进 B，
   而且没有任何报错——`capture_start` 会正常成功。当前部署只有单台是有效配置，
   多台并存属于未支持场景。
2. 排查时容易误判。socket 存在、`ListNames` 里有 `org.qemu`、`capture_input_ready()`
   为真，全部正常，但那是另一台 VM。**校对持有者 PID 是唯一可靠办法**：

   ```sh
   export DBUS_SESSION_BUS_ADDRESS=unix:path=/run/virtconsole/dbus
   pid=$(dbus-send --print-reply --dest=org.freedesktop.DBus /org/freedesktop/DBus \
     org.freedesktop.DBus.GetConnectionUnixProcessID string:org.qemu | tail -1 | awk '{print $2}')
   qm list | awk -v P="$pid" '$6==P'   # 这才是真正被采集的那台
   ```

要同时支持多台，得**每台一条总线**（socket 名带 vmid，如
`/run/virtconsole/dbus-9200`），进入时把地址传给 `capture_start` 的 `bus_addr`。
接口已经支持，缺的是部署侧按 vmid 起总线 + 前端传参。属于设计变更，未实施。

### 3.5 启动竞态

应用服务第二条 `ExecStartPre` 轮询等 Wayland socket（最多 30s）：

```text
for i in $(seq 1 30); do [ -S /run/virtconsole/wayland-0 ] && exit 0; sleep 1; done; exit 1
```

Weston 必须显式 `--socket=wayland-0`，否则名字会漂到 `wayland-1`。

## 四、环境自检

`scripts/check.sh`（68 行，安装前与排障都用）逐项检查并统计 PASS/FAIL：

1. GPU 与渲染节点（应同时有 `card*` 与 `renderD*`）
2. Weston 是否存在
3. Wayland socket（`/run/virtconsole`）
4. seatd（非 root 跑 Weston 必需）
5. NVIDIA 驱动加载状态
6. 内核模块（预留：后续 SR-IOV / Looking-Glass 需要 `kvmfr`）

模式 2 前置能力另有专用脚本 `scripts/spike-qemu-check.sh`（101 行）：
查 QEMU 版本、**`-display` 是否支持 `dbus`**、GL 库（gbm/egl/epoxy/drm）、
GBM/Mesa EGL、渲染节点、`nvidia_drm` 模块、D-Bus 总线可用性。任一 FAIL 则退出码非 0。

## 五、日常运维

```bash
systemctl status virtconsole-weston virtconsole
journalctl -u virtconsole -f          # 应用日志
journalctl -u virtconsole-weston -n 50

systemctl restart virtconsole         # 只重启应用（不动 Weston）
systemctl stop virtconsole-weston     # 释放 HDMI（同时会停应用）
```

配置文件在应用配置目录的 `config.json`，字段表见 [20-架构总览.md](20-架构总览.md) §六。
`VIRTCONSOLE_AUTOCONNECT_VMID=9000` 写在 unit 里，改开机直连目标改这里或改配置。

## 六、故障表（已归档的真实坑）

| 问题 | 现象 | 解法 |
|---|---|---|
| 内核 7.0 不支持旧驱动 | 550 DKMS 编译失败（`VMA_LOCK_OFFSET`） | 换 NVIDIA 官方源装 610 |
| Blackwell 拒载闭源驱动 | `RmInitAdapter failed` | 改用 `nvidia-open` |
| gcc-14 偶发 ICE | nvidia-uvm 编译段错误 | 重试 DKMS build |
| systemd `%U` 展开异常 | ExecStartPre 试图创建 `/run/user/0` 失败 | 改用 `RuntimeDirectory=virtconsole`（0700） |
| Weston socket 名漂移 | 出现 `wayland-1` 而非 `wayland-0` | 显式 `--socket=wayland-0` |
| 服务启动竞态 | 应用早于 Weston socket 就绪 | ExecStartPre 轮询等 socket |
| 订阅源 401 | apt update 失败导致脚本中断 | `install.sh` 容忍（`|| true`） |
| NVIDIA 源签名被拒 | SHA1 绑定签名不符合新 apt 策略 | `trusted=yes`（官方 HTTPS 源，风险可控） |
| 前端产物缺失 | `cargo build` 报找不到 `ui/dist` | 先 `npm run build` |
| 模式 2 连不上 | dbus 采集初始化失败 | 确认 QEMU 与应用同一条 `DBUS_SESSION_BUS_ADDRESS` |
| 模式 2 连不上，且看起来像「键鼠无效」 | QEMU 被孤立在已死的旧总线上（总线曾随 vc-ui 重启而重建） | `dbus-send --session --dest=org.freedesktop.DBus --print-reply /org/freedesktop/DBus org.freedesktop.DBus.ListNames \| grep org.qemu`；查不到就重启该 VM。根治见 §3.4 |
| 采集一切正常但键鼠打到别的 VM | 两台 VM 同挂一条总线，`org.qemu` 被先启动的那台抢走；采集不按 vmid 选 | 用 `GetConnectionUnixProcessID` 校对持有者 PID（见 §3.4）。同一时刻只让一台 dbus-display VM 在跑 |
| 改了代码真机却没变化 | `install.sh` 的安装步骤没跑，服务仍跑旧二进制 | `ls -l /usr/local/bin/vc-ui` 对时间戳；`install -m 0755 target/release/vc-ui /usr/local/bin/vc-ui` 后 `systemctl restart virtconsole` |

## 七、遗留风险

1. **RTX 5070 Ti 是消费级卡，不支持 SR-IOV**——原 V3.0 的 SR-IOV 路线需换硬件
2. **单 GPU**：直通给 VM 后宿主机就没 GPU 了，需加第二张卡
3. NVIDIA apt 源以 `trusted=yes` 绕过签名校验（官方 HTTPS 源，可接受，关注后续签名更新）
4. PVE 企业订阅源每次 apt 更新报 401，无订阅时建议禁用
5. 应用以 root 运行（QMP 权限），待 ACL 方案落地后降权
6. HDMI 物理画面需人工确认（当前 EDID 是采集卡，从采集端看）
