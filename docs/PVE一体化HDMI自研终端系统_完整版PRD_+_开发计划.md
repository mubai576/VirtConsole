PVE 一体化 HDMI 自研终端系统
 
完整版 PRD 产品需求文档 + 全周期开发计划
 
文档元信息
 
- 项目名称：PVE 一体化 HDMI 自研终端控制系统
- 项目定位：纯自研、无第三方串流、无桌面会话、无容器依赖、适配办公 / 游戏 / SR-IOV 直通三模画面采集、本地 HDMI 大屏终端 + 手机局域网遥控器
- 运行环境：Proxmox VE 宿主机（Debian12）
- 图形底座：Weston Wayland（KMS-DRM 原生）
- 核心技术栈：Tauri2 + Rust + Axum + QMP + Canvas + WebSocket
- 废弃依赖：Docker / X11 / GNOME / Moonlight / VNC/RDP/SPICE/uinput
- 文档版本：V1.1 修订稿
- 修订时间：2026-08-06
- 修订说明：修正 QMP screendump 帧率承诺、virtio-gpu Windows 3D 限制、模式 2 技术链路（dbus-display + dmabuf）、硬件前置要求，并新增 V2.0 前置技术验证里程碑
 
一、项目总览 & 核心设计思想
 
1.1 项目终极目标
 
彻底重构 PVE 本地交互体系：
 
1. 抛弃所有闭源 / 冗余 / 不稳定的传统方案
2. 构建一套完全自研、完全可控、分层适配全虚拟机场景的本地 HDMI 终端系统
3. 实现：本地大屏一体化控制台 + 极简手机遥控器
4. 画面只本地渲染，手机只做指令控制，零推流、无外网依赖、零延迟控制
 
1.2 四大核心设计铁则
 
1. 开发与部署彻底隔离
大部分业务（UI、REST API、终端、遥控协议）可在 Windows/Linux 开发机 Mock 开发；三模画面采集与 QMP 输入必须 PVE 真机验证，各模块 Mock 比例需单独评估。
2. 零系统输入模拟
彻底废弃 uinput，所有虚拟机键鼠输入统一走 QMP 协议原生投递。
3. 场景自适应三模渲染
按虚拟机显卡配置自动选择模式：办公低帧 / 60fps 画面（3D 仅 Linux 客户机）/ SR-IOV 直通满血帧。模式由 VM 配置决定，切换需修改配置并重启虚拟机，不可运行时热切换。
4. 最小运行依赖
无桌面会话、无容器、无多余后台（WebKitGTK 等为图形运行库，非桌面环境），整机只为你的自研应用服务。

二、产品功能需求（完整 PRD）
 
2.1 本地 HDMI 主终端核心功能
 
2.1.1 PVE 虚拟机管理面板
 
- 基于官方 PVE REST API，不修改底层配置文件
- 功能：虚拟机启停、重启、关机、快照、状态监控、CPU / 内存 / 磁盘查看
- 多 VM 切换、开机自启配置、资源占用实时展示
- 兼容所有 PVE 版本升级
 
2.1.2 宿主机网页终端
 
- xterm.js 前端终端界面
- Rust PTY 伪终端后端，直连 PVE 宿主机 Bash
- 完整支持快捷键、翻页、颜色、命令补全
- 完全替代本地 SSH 操作
 
2.1.3 内置 Web 浏览器
 
- Tauri WebView 原生内核
- 支持打开 PVE 后台、任意网页、内网服务
- 独立标签页隔离
 
2.1.4 虚拟机画面渲染系统（核心王牌能力）
 
三层全覆盖自研采集体系
 
模式 1：QMP Screendump 轮询（办公模式）
 
适用：办公、Linux 虚拟机、控制台、低负载场景
 
- 无需虚拟机任何代理
- 无需特殊显卡
- 帧率：1080p 下约 10–15fps（QEMU 每帧 PNG 编码开销限制；降低分辨率可更高，需真机标定）
- 用途：日常运维、浏览、办公
 
模式 2：Virtio-GPU DMABUF 零拷贝（普通游戏模式）
 
适用：无直通、需要 60fps 流畅画面（3D 加速仅 Linux 客户机 virgl 可用；Windows 客户机仅 2D 桌面帧）
 
- QEMU -display dbus 导出 dmabuf，经 D-Bus 传递帧，Rust 导入 Weston 渲染，无轮询、零拷贝
- 原生 60fps 低延迟
- 画面可直接嵌入 Tauri Canvas 一体化界面
- 无需虚拟机安装任何程序
- 前置要求：宿主机有 GPU；PVE 所用 QEMU 需支持 dbus-display / OpenGL（不满足需自编译 QEMU）
 
模式 3：IVSHMEM 共享内存（SR-IOV/VFIO 直通满血模式）
 
适用：VFIO 显卡直通、SR-IOV 虚拟显卡直通、高端游戏虚拟机
 
- 硬件 IOMMU 隔离导致宿主机无法读显存
- 虚拟机内轻量 Agent 抓帧（DXGI）写入 IVSHMEM 共享内存
- 宿主机 Rust 读取共享内存渲染
- 显卡原生满血 60fps，无性能损耗
- 基于开源 Looking-Glass 协议（MIT）实现：先复用其 host 端验证通路，再自研轻量化实现
 
2.1.5 统一虚拟机输入系统
 
全场景统一方案，彻底终结输入痛点
 
- 全线废弃 uinput / 内核模拟 USB
- 统一使用 QMP  input-send-event 
- 直接向虚拟机内核投递鼠标、键盘、触控事件
- 兼容：virtio 显卡 / 独显直通 / SR-IOV VF 全部场景
 
2.2 手机遥控器 App 功能（轻量化、高稳定）
 
核心定位
 
只控指令、不看画面、不推流、不解码
 
支持指令集
 
1. 虚拟机控制：启动 / 停止 / 重启 / 快照
2. 终端快捷指令发送
3. 终端页面 / 虚拟机画面 / 浏览器标签切换
4. 系统状态查询：宿主机负载、VM 运行状态
5. 自定义快捷按键、游戏快捷键下发
 
技术特点
 
- 局域网 WebSocket 私有协议 + Token 鉴权
- 极低功耗、零延迟
- 无任何视频编解码开销
- 完全不依赖 PVE 外网
 
三、技术方案详细规范（V1.1 修订稿）
 
3.1 图形运行底座
 
- 禁用 X11，全程 Wayland
- Weston Kiosk 模式，全屏独占 HDMI
- 开机自动启动，无桌面会话、无任务栏、无多余窗口
 
3.2 画面采集三模自动判断逻辑
 
系统按虚拟机显卡配置自动选择采集模式（读取 VM 配置，非运行时热切换；切换模式需修改配置并重启虚拟机）：
 
1. 若是普通虚拟 VGA → 自动启用 QMP 办公模式
2. 若是 Virtio-GPU → 自动启用 DMABUF 60fps 画面模式（3D 加速仅 Linux 客户机可用）
3. 若是 SR-IOV/VFIO 直通显卡 → 自动启用 IVSHMEM 共享内存满血模式
 
3.3 通信协议规范
 
1. 虚拟机控制：QMP Unix Socket（本地无网络开销）
2. 手机遥控：WebSocket JSON 私有协议
3. PVE 管理：官方 HTTPS REST API
4. 画面帧传递：模式 2 走 QEMU dbus-display + dmabuf；模式 3 走 IVSHMEM 共享内存
 
3.4 音频说明（当前版本不实现）
 
V1.0/V2.0 暂不处理音频，V3.0 统一追加 PulseAudio 重定向
 
四、部署体系需求（新增完整工程化能力）
 
4.1 必须配套自研部署脚本体系
 
为保证环境一致性、可复现、可批量部署、零手动配置，项目附带三套脚本：
 
1. 主安装脚本  install.sh 
 
支持三大指令：
 
-  install ：一键安装全部依赖、配置 Weston、配置 Systemd、配置权限、加载内核模块
-  check ：环境自检、输出所有故障点
-  remove ：无损卸载、恢复原生 PVE 环境
 
2. 虚拟机直通辅助脚本  vm-add-ivshmem.sh 
 
- 自动为指定 VMID 添加 IVSHMEM-PLAIN 共享内存设备
- 自动检测虚拟机状态，关机才可修改
- 自动写入 QEMU 参数，无需手动改 conf
 
4.2 系统服务开机自启顺序
 
1. 内核模块加载（ivshmem、drm）
2. Weston Wayland 服务启动
3. 等待 Wayland Socket 就绪
4. 启动 Tauri 主程序

4.3 硬件前置要求（决定版本可达性）

- 模式 2（virtio-gpu 60fps）：宿主机必须有 GPU（QEMU GL 渲染与 Weston 合成均需要），建议独立于直通卡
- 模式 3（SR-IOV/VFIO）：需支持 SR-IOV / vGPU 的显卡（Intel / AMD / NVIDIA 对应型号），普通消费卡多数不支持
- PVE 默认 QEMU 需确认支持 dbus-display / OpenGL；不满足时需自编译 QEMU 或换用满足条件的发行包
 
五、项目约束、限制、已知坑点（正式归档）
 
5.1 不可解决行业固有约束
 
1. DXGI 桌面复制 API：Windows 最小化 / 锁屏黑屏（所有同类项目通病）
2. SR-IOV 直通硬件隔离：宿主机无法直接读取显存，必须虚拟机 Agent
3. virtio-gpu 无官方 Windows 3D 驱动（virgl 仅 Linux 客户机可用），Windows 游戏 3D 加速需走模式 3 直通；Linux 客户机在部分 UEFI+3D 场景存在兼容问题
 
5.2 项目主动舍弃（设计特性，非缺陷）
 
1. 不做手机视频流、不做远程桌面推流
2. 不使用任何 VNC/RDP/SPICE
3. 不使用 Docker 容器运行 GUI
4. 不使用系统级输入模拟 uinput
